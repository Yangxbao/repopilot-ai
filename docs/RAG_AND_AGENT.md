# 检索、RAG 与 Agent 的实现与限制（RAG_AND_AGENT）

本文如实说明：当前做了什么、怎么做的、边界在哪里。
**没有实现的不会谎称实现了**（例如语义向量检索）。

## 1. 检索层

### 1.1 当前实现：关键词检索（KeywordSearchService）

索引阶段已把每个文本文件的**全文**存进 `file_index.content`。
查询时（`search(repoId, query, topK, extFilter)`）：

1. **分词**：ASCII 词（字母/数字/下划线，长度 ≥2）+ 中文连续片段（长度 ≥2）。
   `UserController 注册流程` → `["usercontroller", "注册流程"]`。
2. **打分**（对每个文件）：
   - 词在内容中出现的次数（截断 50 次）× 词权重（`1.0 + min(len,10)×0.1`，越长的词越具体）；
   - 词出现在**文件路径**中：+10（文件名命中价值高）；
   - 整个查询短语在内容中出现：+15；
   - 得分为 0 → 不进入结果。
3. **命中行**：逐行扫描找出最多 5 个命中行（行号 + 截断 240 字符）——这是证据卡片的原料。
4. 按得分排序取 topK。

`extFilter` 参数支持把检索限制在文档类扩展名（`searchDocuments` 工具用它限定 md/txt/sql/yml/properties/json）。

### 1.2 诚实的规模边界

- 每次查询会把该库**全部**文件内容加载到内存打分——导入限制（≤30MB/库、≤5000 文件）保证了这是亚秒级操作。
- 没有 TF-IDF/BM25、没有倒排索引、没有分词器、没有语义向量。
- 中文匹配是子串级别的：搜"注册"能命中"用户注册流程"，但搜"sign up"不会命中"register"。

### 1.3 演进路径（接口已预留）

`SearchService` 是稳定接口，问答/工具/搜索页都依赖它。后续替换实现即可接入：
TF-IDF 排序 → MySQL FULLTEXT（ngram）→ Embedding 语义检索（`AiProvider` 增加 `embed()`）→
向量库（如 pgvector/Milvus）→ 关键词 + 向量混合检索与重排（RRF）。
**在真实 Embedding 服务配置好之前，应用不会显示任何"语义检索"字样。**

## 2. RAG 上下文组织

问答与 Bug 分析共用同一份"证据"结构（`EvidenceVO`：path/startLine/endLine/snippet/reason）：

- **检索结果 → 证据**（`EvidenceFactory`）：每个命中文件取第一个与最后一个命中行作为区间，
  片段为若干命中行拼合（带行号前缀），reason 说明命中来源与得分。
- **证据 → 提示词**（RemoteAiProvider）：
  - 系统提示明确约束：只基于证据回答；每个结论标注 `[文件路径:行号]`；证据不足必须说"无法确定"；
    区分"有直接证据的结论"与"推测"；给出验证步骤；不得编造文件/类名/行号。
  - Bug 分析要求模型输出**严格 JSON**（给出 schema），解析失败时降级为纯文本（`structured=false`），
    绝不因为格式问题丢弃分析内容。
- **证据 → Mock 回答**：MockAiProvider 直接把证据渲染成"相关代码位置"列表——
  文字是模板，**引用的位置是真实检索结果**，页面全程标注"模拟模式"。
- 上下文体积控制：每条证据片段截断 1200 字符，日志截断 6000 字符，证据条数 ≤8（Bug 分析）/6（问答 topK）。

## 3. Agent 工具层

### 3.1 工具清单（全部只读）

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| searchCode | query(1..200), topK(1..10) | 全库关键词检索，返回文件+命中行 |
| readFile | path, startLine?, endLine? | 读取**已索引**文件的行区间（≤200 行/次，每行截断 240 字符） |
| getFileOutline | path | 类/方法/标题结构（启发式解析） |
| searchDocuments | query, topK | 限定文档类扩展名检索 |
| analyzeIssue | evidence + Bug 原始信息 | 调用 AiProvider 生成结构化报告（流水线的汇总步骤） |

### 3.2 安全与预算

- **白名单**：只有注册在 `ToolRegistry` 的工具能被调用；未注册调用会被拒绝并记录日志。
- **所有权**：每个工具执行时都重新做 `RepoService.getOwned()` 校验（纵深防御）。
- **无文件系统访问**：readFile 读取的是数据库里的索引内容，路径必须是索引内的相对路径——
  模型/参数无法借此读取服务器上的任意文件，更没有 Shell 执行能力。
- **预算**：`ToolRunContext` 限制单次分析最多 `repopilot.agent.max-tool-calls`（默认 8）次调用，
  且整次运行有 120s 截止时间；超限抛 RATE_LIMIT 并记录。
- **审计**：每次调用（成功/失败）都写 `tool_call_log`：参数、结果摘要、耗时、错误信息。

### 3.3 固定流水线 vs 模型自主循环

第一版 Bug 分析采用**固定流水线**（提取 → 按优先级检索 ≤4 轮 → 文档补检 → 汇总）。
理由：行为可复现、成本确定、易测试、无需信任模型的工具选择能力。
ROADMAP 中的 ReAct 升级会让模型在白名单内自主决定下一步调哪个工具，
但白名单、预算、日志、只读约束会原样保留——这些正是安全边界。

### 3.4 关键信息提取（ErrorInfoExtractor，纯 Java 无 AI）

- 异常类名：`([A-Za-z][A-Za-z0-9_]*(?:Exception|Error))`
- `Caused by:` 链 → 简单类名
- 堆栈帧：`at com.foo.Bar.baz(Bar.java:52)` → 类名 + 文件:行
- HTTP 路径：`GET /api/xxx` / URI
- 高频 ASCII 关键词（过滤噪音词表）兜底

提取结果按"类名 > 异常类型 > 文件名 > HTTP 段 > 关键词"构造检索词——
类名通常能精确命中定义与引用，是最有价值的检索信号。

## 4. 已知限制清单

1. 关键词检索无语义能力（见 1.2）。
2. 大纲解析是正则启发式：接口默认方法、复杂注解、跨行签名可能漏判或误判。
3. Mock 模式的"原因分析"是模板句式，仅演示流程；真实分析请配置 Remote。
4. Bug 报告的 JSON 输出依赖模型遵循 schema；不遵循时降级纯文本（structured=false）。
5. 工具 readFile 单次 ≤200 行：超长文件需要分多次读取（预算内）。
6. 流水线的检索轮数（4）与证据数（8）是固定值，未根据代码库规模自适应。
